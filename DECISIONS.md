# Architectural Decisions

## ML Batch Features
- **Customer Segmentation (K-Means)**: We implemented a weekly scheduled K-Means clustering algorithm inside our Airflow DAG (`ml_build_segments.py`). It clusters customers into segments (`High Value`, `Loyal`, `Occasional`, `At Risk`) based on Frequency, Average Order Value (AOV), and Recency. This is run as a batch feature and materialized in `dim_users` as `customer_segment`, avoiding expensive runtime LLM or database computation while answering user questions.

## Caching
- **Query Result Cache**: Implemented a query result caching layer (`src/agent/query_cache.py`) that stores query results based on the SHA256 hash of the normalized SQL (via `sqlglot`). The cache is bounded by a 1-hour TTL and is DAG-aware—if `dbt_build_ai` completes a new run, it invalidates all previous cache entries by writing a timestamp to `metadata/last_ai_run.txt`.
- **LLM latency (Phase B)**: Per-node model + reasoning effort live in `router_config.NODE_LLM_PROFILES` (intent on the 20b model at low effort; planning and SQL generation stay as two separate calls on the 120b model by design). `CircuitBreakerLLM` is the single retry layer (tenacity at the router removed for LLM calls), has a wall-time cap, shares breaker state per provider+model, and has a native `ainvoke`. Deterministic prompts are cached by `src/agent/llm_cache.py` (key = namespace + model + full prompt text). The router classifies the route and prefetches the analyst intent in parallel; independent `sql_repair` calls and the LLM `result_analyzer`/`driver_analysis` pair run concurrently via `src/agent/concurrency.py`.
- **ETL removed**: the ETL/scraping agent, `src/tools/*`, the ETL CLI and the ETL/polish routes were deleted to focus on the core Data & AI analytics pipeline. (Superseded: the router now has five routes — ANALYSIS, GENERAL, ADVISOR, FOLLOWUP and PERIOD_CHANGE; see below.)
- **DB layer (Phase C)**: `DatabricksUtil` uses a bounded connection pool (`DB_POOL_SIZE`, default 3). Independent queries run concurrently with result order preserved, and a connection-level failure discards that connection and retries once on a fresh one. The Gold schema is introspected in parallel, cached for `SCHEMA_CACHE_TTL_SECONDS` (default 1h) and invalidated by `metadata/last_ai_run.txt`. `warm_up_db()` runs in the background at app start. `query_cache` writes atomically, has an in-memory LRU, evicts by TTL/entry count/bytes, coalesces identical concurrent queries, and exposes hit/miss counters (`get_stats()`).
- **Lean Phase E (static data)**: dbt runs with `threads: 8`; `silver_orders`/`fact_orders` are incremental merges on `order_id` (timestamp watermark + 3-day lookback) and `silver_order_items`/`fact_order_items` are incremental merges on `order_item_id` (anti-join on loaded keys). `dbt build --full-refresh` rebuilds from scratch. `enrich_reviews` is incremental, deduplicated, batched (25 reviews/request) and async with bounded concurrency and `retry-after` backoff; it is capped by `ENRICH_MAX_REVIEWS` (default 500, 0 = all). `ml_build_segments` loads via one Parquet file + `PUT` into a Unity Catalog volume + `CREATE OR REPLACE TABLE ... AS SELECT` instead of row-by-row INSERTs. The DAG has retries with backoff, per-task and per-run timeouts and `max_active_runs=1`.


## Conversation correctness (top-N, memory, advisor)
- **Top-N / direction are parsed deterministically** (`src/agent/query_intent.py`) and injected into the intent; the fast-path SQL uses them (`LIMIT <n>`, `ORDER BY ... ASC|DESC`) instead of a hardcoded `LIMIT 5`. The fast path is skipped when a `time_period` is present so the period is never silently dropped.
- **Empty vs NULL vs zero** (`src/agent/result_classifier.py`): no-rows and all-NULL/0 aggregate results are explained deterministically (with the warehouse's real date coverage), never narrated by the LLM, and never silently re-run for a different period.
- **Opinion/decision questions route to `ADVISOR`** (`src/agent/advisor.py`): answered from the stored rows only, with the decision criterion, measured facts, calculated findings, limits (no cost/profit/trend data) and next analyses kept separate. Without prior rows it first fetches the top restaurants by revenue through the normal guarded analyst.
- **Memory**: a turn that returns no rows (refusal, error, chart-only follow-up) no longer overwrites the last real result; per-turn fields (chart, latency, LLM-call count) are reset at the router so they cannot leak from the previous turn.

## Diagnosis, enrichment and decision support (follow-ups)
- **FOLLOWUP route** (`src/agent/followups.py`, `src/agent/diagnostics.py`): "why / where is the problem / what should I do" and "add their city and rating" on the restaurants already on screen are handled deterministically, never re-planned by the LLM. Enrichment keeps the same restaurants, order and metric values.
- **Diagnosis** measures each restaurant against the platform, its city and its cuisine (orders per branch percentile, failed-order rate, delivery time, customer rating, listing rating, discount rate, basket size, repeat purchase, 6-month trend, listing age), decomposes revenue into branches × orders per branch × basket, ranks deviations as root-cause candidates with a confidence level (low below 30 orders), attaches an action with a target KPI to each, lists what was checked and is normal, and states measured data-quality limits (e.g. `cost` / `rating_count` are 100% NULL in `dim_resturant`).
- **Databricks string literals**: apostrophes are backslash-escaped. `'McDonald''s'` is two concatenated literals in Spark SQL (= `McDonalds`) and silently matches nothing; the SQL prompt now says so too.
- **Profit questions** on a ranking/lookup are answered with revenue plus a prominent disclosure (profit needs cost data); "why did profit drop" is still refused.
- **Dimension from the question**: the ranked entity is read from the question itself (customer / restaurant / city / cuisine) and overrides a dimension the intent LLM carried over from context. Customers are grouped by `user_id, name` (names are not unique).
- **Router resilience**: when the router LLM fails (429, malformed tool call), questions containing data terms go to the analyst, not to GENERAL. Long answers are clipped to 600 chars in routing/intent context (they pushed requests to ~3.5k tokens).
- **Tests use isolated caches** (`tests/conftest.py`): mocked warehouse rows were being written into the real query cache and served to users.


## RCA accuracy, observability and cache freshness (Oct 2026 audit)
- **Observability first**: executed SQL is logged per query to `eval/executed_sql.jsonl` (cache hit, rows, seconds, error) and telemetry carries `finish_reason`, so empty or wrong results and cache behavior are verified from logs instead of inferred from latency. The UI LLM-call counter counts real telemetry records. Tests redirect both logs to temp files (`tests/conftest.py`).
- **Derived measures** (`query_intent.extract_derived_measures`, `metrics_registry.split_derived_metric`): "percentage contribution / share of total" is split off the metric name, so `percentage_of_total_revenue` resolves to `revenue` plus a SQL column `ROUND(100 * SUM(m) / SUM(SUM(m)) OVER (), 2)` evaluated before `LIMIT`. Only additive metrics (`ADDITIVE_METRICS`) take the fast path; others go to the planner. A requested column missing from the result is disclosed, not dropped.
- **PERIOD_CHANGE route** (`src/agent/period_change.py`): "biggest week/month drop/rise" is decided by the router before any LLM call and answered by three guarded queries (extreme period, brand contribution, measured drivers). Whole periods inside the data coverage only (the old WoW template counted a partial last week and grouped by `(year, WEEK())`). The answer compares the change with normal variability (z < 3.5 is reported as consistent with chance), notes regression to the mean, and states that it is association, not cause. Verified live against an independent Python computation. Dates interpolated into SQL are validated by full match.
- **Diagnosis accuracy**: the ranked metric is read from the previous result's columns (`followups.ranked_metric`); for an order-count question the basket-size factor is removed from the decomposition and the causes. Below 30 orders, failed-order findings need the 95% Wilson lower bound above the benchmark. "Below same-city peers" is `symptom` context, not a root cause.
- **Cache freshness**: the DAG writes `metadata/last_ai_run.txt` after `dbt_build_core` as well as `dbt_build_ai` (Gold facts change at the core build); the data-coverage cache honors the marker.
- **Known gaps**: ties at the top-N cutoff are not disclosed; the UI "confidence" is the router's route confidence, not answer quality; a cold warehouse adds ~25–30 s to the first query after idle.
